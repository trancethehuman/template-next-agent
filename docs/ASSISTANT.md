# Always-on assistant demo

Open `/assistant` and sign in with Google. It has four tabs: **Chat**, **Always-on**, **Live run**, and **Inbox**. The page pairs a durable EVE conversation with a task inbox and inspectable Workflow activity. It implements the [meeting-preparation lesson](https://app.notion.com/p/hai-the-dude/Build-an-Always-On-Personal-Assistant-Like-Muse-and-Dot-with-Vercel-eve-and-the-AI-SDK-3ff836f4a1b381ff9725e53b5769b332): an assistant remembers an explicit preference, continues bounded work after the browser closes, surfaces progress for review, and avoids delivering the same update twice.

## Teaching with the live run

Before a run exists, the **Live run** tab shows the whole flow as a diagram with one sentence and **Start demo**, so students see the shape of the loop before anything runs. **Start demo** creates a guided fictional meeting-prep run with the request “Prepare me for tomorrow’s product design review.” and opens it. The run ID is kept in the URL (`?view=run&run=…`), so reloading or returning later restores the same run. The tab is built for presenting on a shared screen.

- **Flow diagram.** A top-down diagram on the left. The request sits at the top, with the time it arrived. Below it, the stages run downward: Start, Read, Prepare, Review, Deliver, Watch, and Finish. A dashed arrow from Watch back to Read shows the loop. Before the run starts, each stage has one line saying what it will do (for example `Checks the calendar and notes`). Once it is under way, only the stage in focus keeps a line: its live state while current (`Up next`, `Your turn`, `Asleep · check 1 of 3`), or the recorded fact when you select a finished stage (`Version 1 · first read`, `3 bullets · links`). The other stages show just their names, so the eye goes to one place. Finished stages show a check, or an X, square, or alert for declined, stopped, or failed. Calendar event proposals use three stages: Review, Create, Finish.
- **Stage controls.** Select any stage. A stage that has run opens its latest recorded step. A stage that hasn't run yet opens a short explanation of what it will do. Each stage also has a control, shown when you hover or select it:
  - **Play to here** (on stages ahead of a guided gate) plays the run and pauses before that stage runs. The workflow enforces the stop, so it holds even if the page is closed. While playing, the status says `Playing · pauses before Prepare` and the target stage says `Playback pauses here`. Play still stops for your approval at Review and for a trigger at Watch, so only stages up to the next of those are offered.
  - **Start from here** (on rehearsal stages that have already run) starts a new run from that stage's recorded checkpoint. Start begins again from the beginning.
- **Current step.** The panel on the right holds everything happening now: the run status (for example `Paused · press Next step to continue`), the step's title and recorded detail, a one-line teaching note naming the stage's concept (for example **Approval boundary**), source versions with change badges, and any output. On the first gate of a new demo it explains how to begin. Below that, only decisions the controls can't make appear: approve or decline the exact brief or draft, send a trigger while asleep (**Replay the same event**, **Simulate a meeting change**, **Finish monitoring**, with the expected outcome in each tooltip), or **Run it again** after the run ends. A demo gate's recorded detail repeats the status, so it is not shown. Viewing an earlier step replaces the status with **Earlier step**, **Start from here**, and **Back to live**.
- **Controls.** The bottom of the panel has **Play**/**Pause**, **Next step**, and **Stop**. They map onto the server's allowed actions and never invent one; a control the server doesn't offer right now is hidden. **Next step** is the primary button while stepping. While monitoring, Pause becomes **Pause monitoring** and Next step becomes **Check now**. Presenter shortcuts appear in the button tooltips: <kbd>Space</kbd> play/pause, <kbd>N</kbd> next step, <kbd>←</kbd>/<kbd>→</kbd> browse, <kbd>L</kbd> live. Shortcuts are ignored while typing or inside dialogs.
- **Show all steps and memory.** Folded away by default. It lists every recorded step and the durable task state: checks used, last version read, last version delivered, inbox updates, duplicates prevented, and approval.
- **Disconnect viewer.** Stops this page from polling, like closing the tab, and disables controls. The workflow keeps running on the server. **Reconnect** reports how many steps were recorded while away, marks them **New** in the step list, and offers **Show what I missed**. Press Play, disconnect, wait, and reconnect to show durable progress.

**Run next step** executes one real stage, then waits. **Play** uses durable one-second pacing and stops for owner approval or a monitoring trigger. Pausing stops playback at the next safe gate. Approving a brief returns to a manual delivery gate so you can explain the decision before publishing it to the inbox.

Choose **Start from here** on a stage or an earlier step, or use **Start over** to restart from the beginning. A restart creates a new owned workflow, restores the server-recorded state before the selected operation, and links back to the source run. Active rehearsals stop after the replacement is created; their history remains. Source reads and preparation execute again rather than replaying a visual animation. Reused brief context is labeled restored. Live Calendar read/preparation restarts use a fresh read where separate historical source fields are unavailable. Calendar-event restarts always require a fresh approval of the exact draft and preserve its original provider event identity to prevent duplicate creation. Expired event drafts require a new proposal.

Beside the chat, under the cloud browser, one line names the selected workflow and its status; select it to open the run. The full task list is in the **Inbox** tab. Tool calls in the chat appear as one line each; select one to see its raw result. Replayed event IDs appear once. A source comparison distinguishes its first read, an unchanged version, and a changed version. Missing terminal checkpoints are labeled as run-reported states rather than invented events. Elapsed time includes waits. Calendar drafts still show their exact details before approval. See [demo verification](ASSISTANT-DEMONSTRATION-TESTING.md) for automated and real-runtime acceptance.

## Always-on: your calendar

The **Always-on** tab has two views: **Your calendar** and **Example week**. **Your calendar** runs a real, read-only watch over the signed-in user's primary Google Calendar. If the calendar isn't connected yet, the same screen offers **Connect Google Calendar**; it replaces the old Calendar tab, and old `?view=connections` links land here.

**Start watching** creates a `calendar_watch` run on the same diagram as the live run: Start, Read, Notice, Message, Schedule, Finish. Each check:

- **Reads** the next 7 days, including cancellations and each guest's reply (up to 100 events).
- **Notices**, in deterministic code with no model call: clashes between meetings you're attending, cancellations by someone else, meetings that moved since the last check, guests who declined (meetings of 12 guests or fewer), invites you haven't answered, and days with three or more meetings and no break. Free time, working-location markers, and meetings you declined never clash.
- **Messages you**, and only you, in the assistant inbox. Each finding is sent once; a later check messages only what is new. The first check always sends a message, even when everything looks clear. Because nothing goes to another person, there is no approval step.
- **Schedules its own next check**: 15 minutes before your next meeting, or in two hours if nothing is coming up sooner. The diagram shows the time and the same moment as a one-off cron line. **Check now** wakes it early, which is the quickest way to show it noticing a change: move or cancel a meeting in Google Calendar, then press **Check now**.

A watch runs at most five checks, then ends. **Pause monitoring**, **Stop**, and **Start over** work as in the live run. It never changes the calendar, sends email, or contacts anyone. The **Live run** tab keeps the guided demo and any other task you open from the inbox; a watch always opens under **Always-on**.

The Inbox shows **Draft event** when calendar writes are enabled, in place of the old Calendar tab's button.

## Always-on: example week (mocked)

**Example week** shows behaviour that needs more than a calendar, such as following up on email replies, so you can teach the difference between a task agent and an always-on agent. It is a scripted story that runs in the browser. The people (Sam, Priya, Alex), calendar, email, and times are fictional. Nothing is read or sent, and no Google or Gmail access is needed. The tab is labelled **Mocked story**.

The story follows one request, “Prepare me for Thursday’s product design review,” from Monday 4:00 PM to Thursday 3:00 PM across seven checks. Only the first check is a request. The agent starts the rest itself, from its own schedule or from a new email. It uses the same top-down diagram as the live run, with an extra **Notice** stage, and **Watch** labelled **Schedule**.

- **Scenarios.** The **Jump to a scenario** picker opens one behaviour at a time, paused on its first step. **Play** then stops at the end of that scenario. The scenarios are:
  - **Whole week**
  - **Spots blind spots**: a clash with a 1:1, a reviewer who declined, and a decision with no owner.
  - **Schedules its own checks**: it picks wake-up times, each shown with an equivalent cron expression, then wakes itself.
  - **Nudges when nobody replies**: Sam hasn't answered in 3 days, so it drafts a nudge.
  - **Follows up on a reply**: Sam's reply wakes it early, closes one loop, and opens a new one for the promise you made.
  - **Re-plans when plans change**: the meeting moves, so it updates the brief and moves its own checks.
  - **Stays quiet**: nothing changed, so it sends nothing.
- **Task agent vs always-on.** When a step is something a task agent would have missed, such as Sam's reply or the meeting moving, the step says so in one line. The last step lists everything it missed. **Compare with a task agent**, folded away below the diagram, opens a table of when each agent starts, what it looks at, follow-ups, memory, and when it stops.
- **Controls.** **Play**/**Pause**, **Next step**, **Previous step**, and **Restart** (which replays the scenario on screen, or the whole week), with the same <kbd>Space</kbd>, <kbd>N</kbd>, and arrow-key shortcuts as the live run. Each stage offers **Play to here** or **Start from here**, as in the live run. Anything sent to another person stops at **Review**. Approve or decline it, and the delivery step reports what happened. A reminder to you skips Review, to show that the approval boundary is about acting for you.

The live run's intro links here with **How is this different from a task agent?**

## Sign-in and ownership

Google sign-in establishes a verified user identity; it does not grant Calendar permission. Configure `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `AUTH_SECRET` and the exact OAuth redirect URI `/api/auth/callback/google`. Use the actual application origin for `AUTH_URL`. The sign-in client and Calendar connector have separate configuration and consent. See [Calendar setup](ASSISTANT-CALENDAR.md).

The core supports verified Google accounts without an organization-specific default. Set `AUTH_GOOGLE_WORKSPACE_DOMAIN` to restrict access to a verified Workspace domain. The server checks Google's verified email and Workspace claim when that restriction is configured. A prompt or browser-supplied email cannot select an account.

The stable actor ID derives from Google's verified `sub`, not its email address. Each actor has their own chats, tasks, task-format preferences, and Vercel Connect subject for their primary Calendar. The browser stores only its selected conversation ID under a key scoped to that actor; the ID is not an access credential. Signing into a different account starts from that account's own conversation reference.

Private assistant APIs require a verified session. EVE additionally verifies a short-lived, actor-bound origin proof minted by the application proxy, then checks immutable session-creation arguments before reading a transcript or allowing continuation, cancellation, compaction, clearing, or reset. Both creator and authenticated principal must match the current actor. Known foreign run IDs, legacy shared-owner sessions, missing ownership, forwarded principals, forged actor headers, and forged origin stamps cannot grant access. Only the content-free EVE health endpoint is public. The assistant accepts no shared demo bearer, infrastructure OIDC, or anonymous local fallback. The separate transaction demonstration retains its existing `DEMO_ACCESS_TOKEN` gate.

## Two execution modes

**Rehearsal** uses fictional calendar and project-note fixtures. Its brief is deterministic and explicitly labeled synthetic. It still executes real server-side Workflow steps, hooks, durable sleep, cancellation, approval checkpoints, and duplicate suppression. It needs a signed-in account but no Calendar or model credential. Start a queued rehearsal, review its brief, approve delivery to the inbox, replay the source, then change the fixture to demonstrate one relevant update. Denial delivers no notification. The check limit ends monitoring.

**Calendar** reads the signed-in user's primary Google Calendar through Vercel Connect. A bounded AI SDK call prepares a brief from the selected event and requested goal, with real source references. No project-note store, email account, or arbitrary browser is connected. Calendar failures remain failures; the application never silently replaces a live result with a fixture.

A meeting-prep task's approval gate publishes its prepared brief to this user's private task inbox. It does not send an email, invite an attendee, or change an event. The agent cannot approve its own brief or event draft: approval and denial are excluded from `control_task`, and the Next decision endpoint requires the owner's browser session rather than the agent's service credential.

## Calendar event proposals

Calendar access defaults to read-only. Set `ASSISTANT_CALENDAR_WRITE_ENABLED=true` in both runtime services and complete the additional Vercel Connect consent to enable approved event creation. Each user consents independently. An existing read grant does not automatically authorize writing. The proposal tool checks the current create-event capability and returns the actual safe configuration or consent error when unavailable.

When asked to add an event, the agent grounds the date and timezone in Calendar/free-busy and asks for clarification when the title, time, duration or timezone is ambiguous. `propose_calendar_event` accepts one bounded title, optional description, future start/end timestamps with explicit offsets, and an IANA timezone. Shared validation rejects attendees, conference settings, Calendar-ID overrides, past starts, starts more than 365 days away, and durations outside 5–480 whole minutes. It checks availability again and queues only the exact normalized draft. An overlap remains visible; free/busy is a snapshot, not a reservation.

The tool never calls Google's mutation API. Its immutable draft waits for the owner's separate inbox decision. Review the exact title, description, times and timezone before selecting **Create Calendar event**. Changes require canceling the old proposal and creating a new draft. Declining ends the proposal without creating an event. Only the approved durable step creates the private event; invitations and conference data are excluded. The model cannot update or delete events.

An accepted decision means that the workflow received it. The UI keeps the old checkpoint controls disabled until fresh server state advances; an uncertain transport failure retains the same decision ID for a safe retry. A queued task, approval click, or request alone does not confirm a write. `inspect_task` returns the actual `calendarEvent` after success; only a completed calendar-event task with a returned Google event ID confirms creation and its actual link. Credentials remain server-side.

## Chat and task durability

The root `agent/` uses EVE `0.47.7` and the AI SDK. Its model defaults to `openai/gpt-6.1-terra`; see [Models](#models). Typed tools read Calendar/free-busy, start meeting-prep tasks, propose events, inspect progress, start/pause/resume/wake/finish/cancel bounded work, and drive the user's [cloud browser](#cloud-browser). Every tool derives its actor from matching trusted `session.auth.current` and `session.auth.initiator`; no model input can choose a user. Shell, file access, arbitrary server-side web requests, delegation, direct Calendar mutations, and generic framework task tools remain disabled; web pages are reached only through the cloud browser's sandbox. The channel excludes callback, delegated-input and remote-subagent routes.

The browser uses `useEveAgent`. A verified owner can reload the durable transcript and reconnect to a running turn. Closing the page disconnects observation without canceling the server turn. Tasks are separate runs discoverable through that owner's inbox after refresh. Signing out does not cancel already-started bounded work. Session budgets are 3,000,000 provider-reported input tokens and 60,000 output tokens per budget window, with a seven-day lifetime. Browsing sends a screenshot with every action, which is why the input budget is larger than chat alone needs. A budget continuation requires an explicit user action.

On Vercel, execution is independent of the user's laptop. Local execution still needs the server running and the computer awake to execute steps and timers. Closing the browser is supported; sleeping or shutting down the local machine prevents execution until its runtime is running again. Persisted state does not provide continuous local compute.

EVE and Next own separate Workflow queues. Agent task tools call the protected Next API through `agent/lib/task-backend.ts`; they do not start Next functions in EVE's queue. Each request carries a fresh 60-second, purpose-bound service token for the verified actor, signed with the same `AUTH_SECRET` used by both services. Platform protection headers, when configured, do not replace user authority. Redirects are rejected. Stable session/call IDs deduplicate creation and controls, while current checkpoint IDs prevent stale actions from affecting later work.

The bridge origin comes only from trusted server configuration: `ASSISTANT_APP_ORIGIN`, otherwise `https://${VERCEL_URL}` on Vercel, otherwise `http://127.0.0.1:3000` in local development. Configure `ASSISTANT_APP_ORIGIN` for a different local port or HTTPS application origin. Non-loopback HTTP, credentials, paths and query strings are rejected. Missing origin, service authentication or Calendar configuration fails precisely; no account or synthetic fallback is selected.

## Models

The chat header has a model picker. The default is **GPT-6.1 Terra** (`openai/gpt-6.1-terra`). The other choices are GPT-6.1 Sol, GPT-6 Luna, Claude Sonnet 5.5, and Gemini 3.8 Flash, all through AI Gateway, and all able to read screenshots and call tools. The list lives in `lib/assistant/models.ts`.

The choice is saved in an `assistant-model` cookie and applies from the next message; switching mid-conversation re-reads the history at the new model's uncached price. The server accepts only allow-listed IDs: the EVE auth step adds the choice to the signed-in principal, and a dynamic model in `agent/agent.ts` reads it at each turn. A missing or unknown value falls back to the default. Meeting-prep tasks started from the chat or the inbox use the same choice for their brief; `ASSISTANT_MODEL` sets the brief model when there is none.

## Cloud browser

Each signed-in user has one cloud browser: Google Chrome on a 1024×768 desktop inside a persistent Vercel Sandbox. The user can use it directly, and the assistant can use it for them. The live view follows Vercel's AI SDK Computer Use template, with ownership, a protected view, and checkout limits added.

- **Open it anytime.** The **Browser** button in the page header, or **Start** / **Resume** in the browser panel beside the chat, starts it without asking the assistant. The first start for an account installs Chrome, the desktop, and agent-browser, which takes about a minute. Later starts resume in a few seconds.
- **Saved and resumable.** The sandbox is persistent: when it stops, Vercel snapshots its disk, and the next start boots from that snapshot. Only the disk survives, not running programs, so the app saves what matters to disk. Chrome keeps its own profile (cookies, sign-ins, history), starts with `--restore-last-session`, and the app also saves the open tabs and reopens them if Chrome comes back blank. **Stop** saves the tabs and closes Chrome cleanly before stopping. **Idle shutdown.** The browser sleeps, saved the same way, 30 minutes after its last use: a start or resume, an agent action, or **Keep awake**. Watching does not count, so a forgotten tab cannot keep it running. The panel offers **Keep awake** five minutes before it sleeps, and the large view shows the sleep time. Set `ASSISTANT_BROWSER_IDLE_MINUTES` to change the window; it is clamped to 5–60 minutes. Hobby sessions still end at 45 minutes; the next start resumes from the saved disk. Snapshots expire 30 days after their last use, and only the latest one is kept.
- **How the assistant drives it.** The `browser` tool uses [agent-browser](https://github.com/vercel-labs/agent-browser) `0.41.0`, attached over Chrome's local debugging port to the same Chrome the user watches. Each action (navigate, snapshot, click, fill, type, press, select, scroll, back, wait, screenshot, close) returns the page title, address, and its interactive elements with refs such as `@e3`, so the assistant clicks and fills by ref instead of guessing coordinates. agent-desktop was considered and not used: it automates native desktop apps, and its own docs point web pages to agent-browser.
- **Screenshots in the chat.** Every action appears as a row, such as “Clicking @e3”, with a screenshot of the page right after it. Select a screenshot to see it full size. The model reads the element list after each action and receives the image only when it asks to look, which keeps long browsing tasks affordable.
- **Approval.** The first browser action in a conversation waits for the user's approval in the chat.
- **Live view.** The panel beside the chat shows the browser as it works. On wide screens, drag the divider between the chat and the panel to make the live view bigger; the split is remembered in that browser, and double-clicking the divider resets it. Selecting the view opens a large view. It is watch-only until the user presses **Take control**, so the user can finish a sign-in or payment themselves. The view is noVNC from the sandbox's own HTTPS address, protected by a VNC password derived from `AUTH_SECRET`. Only the owner's `/api/assistant/browser` request returns that address.
- **Limits.** The assistant never signs in, creates accounts, enters payment or personal details, accepts terms, solves CAPTCHAs, or completes a purchase. It stops where a site asks for an account, contact details, or payment, and says what is ready. The tool also refuses to type anything shaped like a payment card number. Page text is untrusted data. Some large ticket sites block browsers that run in a data center; the assistant reports that and tries another site.

`/api/assistant/browser` supports `GET` (status, never wakes the browser), `POST {"action":"open"}` (start or resume), `POST {"action":"keepalive"}` (the owner's Keep awake: a full idle window from now; the page never sends it on its own), and `DELETE` (save and stop). Sandbox credentials come from `VERCEL_OIDC_TOKEN` locally (`vercel env pull`, valid about 12 hours) and from project OIDC on Vercel. Set `ASSISTANT_BROWSER_ENABLED=false` to turn the browser off. Sandboxes are billed while running, and the live-view port counts as traffic.

## Explicit preferences

Ask: “Remember that I want three bullets with source links.” `save_preference` stores only the supported brief format plus that exact explicit request and originating turn ID in an EVE `defineState` slot. `read_preference` reads it back; `forget_preference` clears the active value. It survives turns and reconnects in that owner's conversation. A new conversation has separate state; this is not cross-conversation memory. New tasks receive a snapshot of the saved format. Credentials and private Calendar content are not preferences.

The page's task-format setting is separate, actor-scoped application state. Saves create small completed preference workflows, and the newest owned record supplies that user's current default and provenance. Reset appends a default-format record. Changing one preference surface does not implicitly update the other. Forgetting an active preference does not delete prior messages or workflow history.

## Storage and retention

Auth.js stores its session in an encrypted HttpOnly cookie; this feature adds no user database. Vercel Connect holds provider grants and tokens. Calendar fields, chat messages, task goals, and bounded tool results can reach the configured model through AI Gateway. A calendar watch never calls a model. The model never receives OAuth tokens, the session cookie, proxy proofs, service tokens or environment secrets. Treat fetched event titles, descriptions and notes as untrusted data.

EVE conversation content, preferences, task inputs, actor identity and task activity persist in the backing Workflow Worlds. Task ownership is seeded in canonical workflow metadata before execution and checked before reading inputs or streams. The local Next task/preference store is the ignored repository-root `.workflow-data` directory. EVE explicitly uses its separate ignored `.eve/.workflow-data` World. Vercel uses its managed World. There is no new transaction database or general file store.

A calendar watch persists, in its Workflow run: the number of events read; each flagged item's title, time, and wording; the first names of guests who declined; the message sent to the owner; and, between checks, the titles and times of upcoming events so it can tell what moved or disappeared. Guest email addresses are hashed before they leave the read step and are not stored. This follows the same retention as other Calendar task activity.

The persistent local paths are outside `.next`: the pinned adapter's old `.next/workflow-data` default was vulnerable to production-build cleanup. Never delete the persistent directories as a build-cleanup step. Back them up if their history matters. Stop the server before explicitly migrating an older data directory; changing configuration does not migrate records. Existing legacy sessions, tasks and preferences without verified ownership remain unexposed and are not automatically assigned to a user or deleted.

The inbox includes pending/running work alongside recent owned tasks. Creation is capped at 20 active tasks per user. Each meeting-prep task performs at most five checks, normally 15 minutes apart, with an initial delay of at most 24 hours. Queued, approval and manually paused checkpoints wait for the owner. Canceling a task, expiring a session, clearing active preferences, signing out or opening a new chat does not hard-delete runtime history or an already-created Google event. Configure provider/World retention and deletion before using sensitive real data. Authentication and bounded workflows are not a comprehensive production abuse or rate-limit system.

## Verification

Use Node.js 24 and Bun:

```sh
bun run test
bun run lint
bun run lint:design
bun run typecheck
bun run build:eve
bun run build
```

The focused agent suite verifies both actors' session ownership on create/continue/read-stream/control boundaries; actual EVE handlers reject foreign owners before attaching runtime handles. It covers legacy and encrypted Workflow argument decoding, forged identity headers and origin proofs, rejected principal forwarding, stable Google subject ownership after an email change, actor-bound tool context, per-actor service signing, secure origins, redirect rejection, idempotency keys, explicit preference bounds, read-only Calendar failure, exact-draft queuing, and the absence of model approval authority. Provider and task suites separately exercise Calendar errors, immutable approval checkpoints, ownership, workflow transitions and duplicate suppression using synthetic data and explicit doubles.

Live local HTTP checks also passed with two cryptographically signed synthetic-user cookies: both created EVE sessions with HTTP 202 and restored their own stored synthetic transcript with HTTP 200. All twelve attempts to stream, continue, cancel, compact, clear or reset the other actor's known session returned HTTP 403. Both owners could reset their own sessions with HTTP 200. A separate actual model turn created a queued synthetic rehearsal through the EVE tool and actor-scoped service-token bridge; its owner read the task with HTTP 200 and a second valid user received HTTP 404. Cleanup cancellation was accepted with HTTP 202. These checks exercised the real local Worlds and proxy rewrite without calling Google Calendar; authentication tokens stayed in process memory.

Rehearse the actual page: sign in, create a queued synthetic task, start it, review its brief, decline or approve, observe sleep, pause/resume, wake, replay without a duplicate notification, change the source once and stop. Reload a running conversation and reopen task activity. Verify narrow layout, keyboard access, draft recovery and reconnect errors. With real consent, separately verify the signed-in account's Calendar read, meeting-prep brief, exact event proposal, owner-only approval and returned Google event link. A fixture run or a signed test session does not verify Google's actual OAuth consent flow.
